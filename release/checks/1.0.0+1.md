## 1. The offline gate

SPEC.md §17's offline gate has three layers and only two of them are mechanical.

### Source graph — automated, green

`test/policy/no_network_test.dart` walks `lib/` for `HttpClient`, `Socket`,
`HttpRequest` and the banned packages; `tools/audit_deps.sh` walks the resolved
dependency graph. Both were re-verified by planting: a `dart:io` `HttpClient`
call in `lib/app/` turned the first red, and the second has its own self-test
arms in `check_gates_selftest.sh`.

**What it proves:** a property of the inputs. It cannot see a dependency that
reaches a socket through a path the pattern list does not name.

### The shipped binary — automated, green, and new

`tools/check_binary_offline.sh` reads the built executable rather than the
source: `nm -u` for imported networking symbols and `otool -L` for linked
networking libraries.

```
ok    no networking symbol imported by Runner
ok    no networking library linked
```

**This gate exists because of the platform decision.** The Android release
carried §17's strongest evidence — `android.permission.INTERNET` provably absent
from the *merged manifest*, a property of the artifact. iOS declares no network
permission at all, so nothing reproduces that, and the epic recorded the loss.
This closes part of it from the other end: a link-time fact survives obfuscation
and tree-shaking, so it describes what actually ships.

**Seen to fail.** A scratch bundle was compiled against CFNetwork and the gate
reported both arms red:

```
FAIL: the app binary imports networking symbols:
  _CFHTTPMessageCreateRequest
FAIL: the app binary links a networking library:
  /System/Library/Frameworks/CFNetwork.framework/…
```

**What it proves:** the binary imports nothing that could open a connection.
It does not prove that no system service acts on the app's behalf.

### Aeroplane mode from a clean install — NOT DONE

**This is the part that is missing, and it is the part §17 actually asks for.**
A simulator has no flight mode: it borrows the host's networking, and toggling
the Mac's Wi-Fi tests the Mac. The pass has to happen on real hardware — install
from TestFlight onto a device that has never run Odova, put it in aeroplane
mode, complete first run, log a fill-up and a service, export a backup, and
confirm every screen works and nothing waits on a timeout.

It is **blocked behind Task 19.10**, which is itself blocked (below), because it
must be performed on the artifact that will be released rather than on a debug
build. Recorded here as outstanding rather than quietly satisfied by the two
gates above, which answer a narrower question.

## 2. Upgrade over an installed build — NOT APPLICABLE, with the reason

There is no previous release. `release/uploaded-build-numbers.txt` is empty,
nothing has been submitted, and there is no shipped schema for a migration to
run from. The check is not applicable for 1.0.0+1 and becomes mandatory for
1.0.1 and every version after it: install the previous *store* build, add data
under it, upgrade in place, and confirm the history is intact.

`run-migration`'s warning applies from then on — a schema-shape check passes on
a migration that copies zero rows, so the assertion has to be about the DATA and
not about the columns.

## 3. What blocks the release today

**The design review is NOT SIGNED.** `design/review/SIGNOFF-2026-09-08.md` says
so and says why: the band profile fails on 106 of 112 parity comparisons and no
release build has ever been looked at. EPIC-19 makes that file a precondition of
the ritual, `tools/release.sh` checks it, and the dry run refuses:

```
FAIL  design review is not signed off (design/review/SIGNOFF-2026-09-08.md)
FAIL  release/checks/1.0.0+1.md is missing        ← this file, now present
FAIL  CHANGELOG.md has no 1.0.0 section
```

Signing that file to unblock a checklist would make the epic's first assumption
false. It stays unsigned until the parity work behind it is done.
